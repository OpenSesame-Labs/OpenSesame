# Authentication and authorization state-machine inventory

This is a source-backed starting inventory, not an exhaustive discovery of
every implicit state machine. A protocol named here is a source of requirements
to evaluate; its mention is not a claim of conformance. Priorities reflect the
potential effect of a failed boundary, not evidence that a vulnerability exists.

Evidence labels describe the kind of artifact found:

- **Model-checked** means a finite TLA+ model is present and checked by the
  behavior-model runner. **Lean model proof** means Lean checks the named
  mathematical predicates and theorems. Neither label proves the application
  implementation, the standard, or the environment.
- **Tests present** means the named tests exist. They exercise specific cases;
  this inventory does not claim they cover all states, all implementations,
  or that every listed suite was run for this document.
- **Unassessed** means this inventory did not establish a proof or identify
  sufficient evidence for that property. It does not mean that no test exists.

The priorities are P0 for credential issuance, authentication, approval and
authority boundaries; P1 for adjacent session and lifecycle behavior. A P0 item
can have useful tests or an abstract proof and still have open obligations.

## Proof and discovery work still required

For each candidate, first record the exact standard version and supported
profile, the application entry points and storage boundaries, the adversary and
trusted components. Then specify safety and liveness separately: allowed and
refused transitions, correlation, freshness, expiry, cancellation, replay,
concurrency, failures, restarts and cleanup. Model-check a bounded system with
explicit environment assumptions and use generated traces and adversarial
property tests against the real interfaces.

Lean proofs should establish the intended policy and a defensible link to the
actual implementation: a soundly verified translation/refinement, a proved
kernel actually used by production, or a separately justified code-level proof.
Hand-translated models and generated test vectors are valuable evidence but do
not prove source-code equivalence. State explicitly where cryptographic
algorithms, external libraries, operating systems, browsers, clocks and
databases are assumptions rather than proved components. Check proofs and
conformance tests in release qualification and test that deliberate violations
are detected.

Discovery remains open for other authentication and authorization paths,
including their UI, alternate clients, integrations, transport profiles,
recovery and migration paths, configuration changes and third-party protocol
implementations. Map each to an entry point and evidence before assigning it a
verification status; do not infer coverage from a count of files or models.
